**What is broken (host crontab, globo-pi):** `sync-nba-stats-games-video.sh`, `sync-wnba-games-video.sh`, `buzzer-beater-live-window.sh` and `buzzer-beater-wnba-live-window.sh` all `docker compose exec` into the `buzzer-beater` container, whose image was built 2026-07-30 (`/app/server/lib/nba-schedule.js` dated May 12). That code calls `fetchJson` with no User-Agent; site.api.espn.com (Akamai) 403s UA-less requests since 2026-08-04, so every run dies with `Unexpected token '<', "<HTML><HEA"…` — WNBA scheduler failures are logged under the NBA job id `buzzer-beater-live-scheduler` (the `main().catch` logger is hard-coded). Net effect: no `box_score_increments` for any WNBA game since at least 08-29 and nothing for the NBA preseason (first game 2026-10-03). The noon tennis / WNBA-history syncs still work because they run from Track worktrees (`7c7ab432`, `663e94c5`) that carry the fix (`ESPN_API_HEADERS`, `fetchEspnJsonWithRetry`).

**Why:** the Pi checkout `~/Documents/globo-pi/buzzer-beater` was never pulled/rebuilt after PR #14 (08-05) and PR #18 (08-13) merged; `scripts/deploy-prod-on-pi.sh` (pull main + `docker compose up -d --build buzzer-beater`) was not run. Deploying origin/main fixes the WNBA path and adds the SOCKS retry.

**Separate, needs code:** `https://cdn.nba.com/static/json/staticData/scheduleLeagueV2.json` and `…/liveData/scoreboard/todaysScoreboard_00.json` answer Akamai `Access Denied` 403 (`<HTML><HEAD><TITLE>Access Denied`) from the Pi with every UA (Chrome, curl default, empty, `BuzzerBeater/1.0`), with and without `Referer: https://www.nba.com/`, direct and through every Nord SOCKS host. `stats.nba.com` times out. ESPN's NBA scoreboard (`site.api.espn.com/apis/site/v2/sports/basketball/nba/scoreboard?dates=YYYYMMDD`, with the client UA) returns 200 — the NBA schedule/scoreboard path in `sync-day-games.js` (`fetchSchedule` / `mergeLiveScoreboardForToday`) has to move there, as the WNBA path already does.

**Nord SOCKS auth throttle:** a burst of connections (≈25 in 7 min) makes 6 of 7 `*.socks.nordhold.net` hosts answer `User was rejected by the SOCKS5 server` for a few minutes, then they recover (all 7 back at 200 within ~5 min). It is transient — do not rotate credentials for it; the 08-13 keep-alive/retry commit on origin/main is the mitigation.
